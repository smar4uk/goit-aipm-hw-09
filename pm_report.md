# PM-аналіз ML-експериментів: iris-classification

**Джерела:** MLflow UI (експеримент `iris-classification`, 5 runs), Prometheus (`mlflow_accuracy`, `mlflow_loss`), опис вхідних даних від ментора. Скриншоти лежать у папці `screenshots/`.

## 1. Бізнес-контекст

**Яку задачу вирішує модель.** Модель визначає вид ірису (setosa, versicolor або virginica) за чотирма вимірами квітки: довжиною і шириною чашолистка та пелюстки. Iris — навчальний датасет, тому для аналізу я беру умовний бізнес-сценарій: розсадник або ботанічна лабораторія автоматично сортує зразки за видами, щоб співробітник не визначав кожну квітку вручну.

**Яке рішення підтримує.** Модель автоматично ставить мітку виду на зразок. Від цієї мітки залежить, в яку партію чи каталог потрапить квітка.

**Хто користувач.** Співробітник лабораторії або складу, який сортує зразки, а також система обліку, куди записується вид.

**Яка помилка небезпечніша.** Setosa легко відрізнити від інших видів, тому реальні помилки майже завжди між versicolor і virginica. Небезпечна саме **впевнена** помилка: модель на 95% «впевнена», що це virginica, а насправді versicolor. Таку квітку ніхто не перевірить вручну, і вона потрапить не в ту партію. Якщо ж модель сумнівається, зразок можна віддати людині.

**Головна метрика.** Тільки accuracy тут мало, бо вона не показує, на яких класах модель помиляється і наскільки впевнено. Для цієї задачі я б дивився на три речі разом:
1. **accuracy** — загальна частка правильних відповідей;
2. **log loss** — штраф за впевнені помилки, і для нашого сценарію саме це важливо;
3. **recall по кожному класу, особливо versicolor і virginica, плюс confusion matrix** — чи не «просідає» один із видів. Цих метрик у MLflow зараз немає.

## 2. Аналіз runs у MLflow

Test-вибірка — 45 квіток (30% від 150), однакова для всіх runs (`split_random_state = 7`, `test_size = 0.3`). Це важливо: accuracy 0.956 означає 43 правильні з 45, а 0.933 — 42 з 45. **Різниця між ними — одна квітка.**

| Run ID | Run name | Що змінили | Основні параметри | Accuracy | Loss | Artifact є? | Коментар |
|---|---|---|---|---|---|---|---|
| `b31fafa3…` | logreg-baseline | **Baseline** | logistic_regression, C=1.0, max_iter=500 | 0.933 (42/45) | 0.191 | Ні | Добрий простий baseline, сильний для свого розміру |
| `7a26a3a7…` | logreg-strong-reg | Сильна регуляризація | logistic_regression, C=0.01, max_iter=500 | 0.844 (38/45) | 0.686 | Ні | Модель занадто «зажата», гірше за baseline за обома метриками |
| `b9a8191d…` | decision-stump | Найпростіше дерево | decision_tree, max_depth=1 | 0.667 (30/45) | 0.462 | Ні | Дерево з одним розгалуженням фізично не може розрізнити 3 класи. Контрольна нижня межа |
| `4fda11e9…` | rf-small | Інший тип моделі | random_forest, n_estimators=10, max_depth=2 | 0.933 (42/45) | 0.228 | Ні | Та сама accuracy, що в baseline, але loss гірший |
| `2ddc4f9d563c43e5a7c6c8523a580db3` | **rf-depth3** | Більший ліс, глибші дерева | random_forest, n_estimators=100, max_depth=3 | **0.956 (43/45)** | **0.141** | **Так** | Найкращі метрики, єдиний run зі збереженою моделлю |

Повний run ID є лише для rf-depth3 (сторінка run). Для інших я бачу 8-символьний префікс із міток Prometheus.

**Що видно з таблиці:**
- **Різниця між runs зрозуміла:** кожен run має назву, тип моделі й параметри.
- **Але є нюанс з rf-depth3:** порівняно з rf-small змінили одразу два параметри (кількість дерев 10 → 100 і глибину 2 → 3). Тому ми не знаємо, що саме дало покращення.
- **Accuracy і loss не завжди погоджуються.** decision-stump має гіршу accuracy, ніж logreg-strong-reg (0.667 проти 0.844), але кращий loss (0.462 проти 0.686). Те саме з rf-small і baseline: accuracy однакова, а loss різний. Це наочний приклад, чому одна метрика не дає повної картини.

**Чи можна відтворити результат:**

| Run | Відтворюваність |
|---|---|
| Чотири runs без артефакту | Частково. Параметри, `random_state` і спліт записані, `train.py` вказаний як source. Але немає commit-хешу коду, версій бібліотек і збереженої моделі. Можна спробувати перетренувати й сподіватися на той самий результат |
| rf-depth3 | Модель збережена разом із `requirements.txt`, `conda.yaml` і `python_env.yaml`, тож середовище відновити можна. Проте **Source порожній («-»)**: невідомо, яким скриптом і з якої версії коду її натреновано. У поле Datasets записано «None», є лише тег `dataset: iris`. Модель не зареєстрована в Model Registry (Registered models: None), а run запущений під користувачем `root` |

## 3. Кандидат на staging: rf-depth3

**Чому саме цей run.** Він найкращий за обома метриками: accuracy 0.956 і найменший loss 0.141. А головне, це **єдиний run, у якого є збережена модель**. Без артефакту передати в staging нічого, навіть найкращу метрику.

**Ключова метрика.** Я ставлю на перше місце log loss, а не accuracy, бо в нашому сценарії найбільше шкодять впевнені помилки. За loss rf-depth3 виграє помітно: 0.141 проти 0.191 у baseline, тобто приблизно на 26% краще.

**Baseline є:** `logreg-baseline`, accuracy 0.933, loss 0.191.

**Наскільки покращення суттєве:**
- За accuracy: +2.2 п.п., тобто **одна** додатково правильно класифікована квітка з 45. На такій маленькій вибірці це може бути випадковістю конкретного спліту.
- За loss покращення відчутніше: модель рідше впевнено помиляється.
- Але це один спліт без cross-validation, тому я б не називав перевагу доведеною.

**Trade-off.** Random forest на 100 дерев складніший і важчий за логістичну регресію. Тренування зайняло 6.6 с проти ~0.36 с, а для inference модель буде більшою і повільнішою. Для Iris це некритично, але виграш одна квітка з 45, а ціна — складніша модель. Якщо в staging важливі швидкість і простота, logreg-baseline — чесна альтернатива, але для неї треба спершу зберегти артефакт.

**Artifact є:** `MLmodel`, `model.skops`, `conda.yaml`, `python_env.yaml`, `requirements.txt`, `input_example.json`, `serving_input_example.json`. Набір повний для serving.

**Чи достатньо інформації для відтворення.** Частково. Модель можна завантажити і запустити, але не можна чесно перетренувати, бо невідомий код (порожній Source) і немає посилання на версію датасету.

## 4. Prometheus / Grafana

Ментор надав скриншоти Prometheus UI (Graph і Table), а не Grafana. Для цього аналізу різниці немає: Grafana Explore показує ті самі метрики з того самого Prometheus.

**Prometheus показує:**
- обидві метрики, `mlflow_accuracy` і `mlflow_loss`, по 5 серій, по одній на run;
- мітки `experiment`, `run_name`, `run_id`, `model_type`, тобто кожну серію можна зв'язати з run у MLflow;
- значення **повністю збігаються** з MLflow UI аж до останнього знака (наприклад, rf-depth3: 0.95555… і 0.14147528385144287 в обох системах);
- найкращий run видно одразу: фіолетова лінія rf-depth3 найвища на графіку accuracy і найнижча на графіку loss.

Що помітив:
- `run_id` у Prometheus скорочений до 8 символів (`2ddc4f9d` замість повного `2ddc4f9d563c…`). Для 5 runs цього достатньо, але при сотнях runs можливі збіги.
- Розрив на графіку близько 08:34 — це перезапуск exporter-а, значення після нього ті самі. Втрат даних немає, але варто мати алерт, якщо exporter впав надовго.
- exporter працює на `127.0.0.1:8000`, тобто це локальний стенд, а не спільна інфраструктура.
- Значення на графіку — горизонтальні лінії: це фінальні метрики тренування, а не поведінка моделі в часі.

**MLflow UI показує:** повний контекст кожного run: параметри, метрики, теги, артефакти, хто і коли запустив, тривалість, source.

**Разом ці інструменти допомагають:** у MLflow розібратися, *що* і *як* натреновано, а в Prometheus/Grafana швидко порівняти runs на одному графіку і в майбутньому налаштувати алерти. Збіг значень підтверджує, що експорт метрик працює коректно.

**Але для production-рішення ще бракує:**
- метрик по класах (recall/precision для versicolor і virginica) і confusion matrix;
- оцінки стабільності: cross-validation або кілька сплітів;
- метрик моделі **в роботі**: якість прогнозів на нових даних, розподіл вхідних даних (drift), latency і помилки inference;
- погоджених порогів (thresholds), нижче яких модель не можна випускати або треба відкотити.

## 5. Production-readiness процесу

| Питання | Так / Ні / Частково | Коментар |
|---|---|---|
| Є baseline для порівняння? | Так | `logreg-baseline` (0.933 / 0.191) |
| Є зрозуміла головна метрика? | Частково | Записані тільки accuracy і loss. Не погоджено, яка з них головна і який мінімальний поріг. Немає метрик по класах |
| Є model artifact? | Частково | Тільки для rf-depth3. Для baseline немає, тож порівнювати чи відкочуватись на нього в serving неможливо |
| Є run ID для кандидата? | Так | `2ddc4f9d563c43e5a7c6c8523a580db3` |
| Є параметри експерименту? | Так | Записані для всіх 5 runs, включно зі сплітом і `random_state` |
| Є метрики в MLflow? | Так | accuracy і loss для всіх runs |
| Є метрики в Grafana / Prometheus? | Так | Обидві метрики з мітками run, значення збігаються з MLflow |
| Є критерій переходу в staging? | Ні | Не зафіксовано, що вважається «досить добре» (наприклад, accuracy ≥ 0.93 і loss ≤ baseline) |

|---|---|---|

## 7. PM decision report

**Рекомендація: Need more experiments.** rf-depth3 — кандидат на staging, але його ще не можна туди переводити.

**Обґрунтування.** rf-depth3 найкращий за обома записаними метриками: accuracy 0.956 проти 0.933 у baseline, log loss 0.141 проти 0.191. Це єдиний run зі збереженою моделлю, готовою до serving. Однак за accuracy перевага — лише одна квітка з 45 на одному спліті, тож вона може бути випадковою. Покращення loss виглядає переконливіше, але й воно не перевірене на інших сплітах.

**Основні докази.** Таблиця runs і сторінка run у MLflow, повний набір артефактів моделі, а також метрики в Prometheus, які точно збігаються з MLflow. Тобто записаним метрикам можна довіряти, сумнів лише в тому, чи достатньо їх для рішення.

**Основні ризики.** Перевага кандидата може не підтвердитись, run не можна чесно відтворити (немає source-коду, версії даних і автора), немає метрик по класах, порогів, rollback-плану і моніторингу після деплою.

**Що потрібно зробити перед staging і production:**
1. Перезапустити baseline і rf-depth3 з cross-validation, логувати модель у кожному run.
2. Додати recall по класах і confusion matrix.
3. Записувати git commit і версію датасету, запускати runs під персональними акаунтами.
4. Погодити пороги, наприклад: loss не гірший за baseline, recall кожного класу ≥ 0.9.
5. Зареєструвати кандидата в Model Registry і мати попередню версію для rollback.
6. Описати моніторинг після деплою (drift, впевненість прогнозів, latency) і призначити owner.

Якщо після cross-validation rf-depth3 стабільно кращий за baseline і проходить пороги, наступне рішення — **Go to staging**. Якщо різниця зникає, варто обрати простішу logreg-baseline: вона менша, швидша і легше пояснюється.
